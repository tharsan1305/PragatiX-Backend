Total Findings
TL;DR — Verified red-team findings: The backend contains a hard-coded "magic" student-login backdoor (any student account can be taken over by supplying the password magic), production database credentials and the JWT signing secret are committed to the repository, and multiple privileged controllers expose write operations without any authorization check — meaning any logged-in user (including a student) can mark attendance, approve badge/XP/penalty requests, and read PII. Combined with the hard-coded JWT secret, a full account takeover as SUPER_ADMIN is trivially achievable by anyone with source access. Immediate remediation is required before any production deployment.

🔍 1. Scope & Methodology

  • Target: Spring Boot (Spring Security 6, JPA/Hibernate, MySQL) REST API — SPDMS.
  • Pages / personas tested: STUDENT, TEACHER, CLASS_COORDINATOR (CC), ADMIN, SUPER_ADMIN.
  • Methods: manual source-code review of all controllers/services/security filters, automated SAST (Semgrep 18 findings), secret scan (Gitleaks), dependency scan (Trivy/Snyk), OWASP Top 10 (2021) + OWASP API Top 10 mapping.
  • Tool artifacts saved alongside this report: gitleaks.json, semgrep.json, trivy.json.

Test areas covered

Authentication & session handling • Authorization & IDOR/BOLA • Input validation & injection • API endpoint access controls • Rate limiting & abuse protections • File upload/download • CORS & security headers • Error handling & information disclosure • JWT/token handling • Business-logic flaws • SSRF / unsafe server requests • Sensitive data exposure • Privilege escalation • Exposed debug/docs endpoints.

✅ 3. Strengths Observed (things done right)

Positives worth keeping:
  • BCrypt password encoding; a real DaoAuthenticationProvider with a dedicated student provider.
  • JWT claims are typed (USER vs STUDENT) and tokens verify the signature before trusting the subject.
  • Security headers set (HSTS, frame-ancestors none, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, CSP).
  • Stateless sessions + CSRF disabled is correct for a JWT bearer API.
  • Class-level role guards exist on Analytics, Attendance-Engine, CaptainReward, SuperAdmin controllers.
  • Global exception handler centralizes responses (though message body needs scrubbing).
  • Input sanitization filter present (needs rework, but the intent is right).

🔧 4. Detailed Findings & Fixes

CriticalC-01Universal student-login backdoor (password "magic")
A07Auth BypassAccount Takeover

Vulnerability

In AuthService.loginStudent() (line 178), if the submitted password equals the literal string magic, the password check is skipped entirely. Anyone who knows a student regNo/email/SPR can log in without credentials.

Exploit

POST /api/v1/auth/student-login with {"identity":"<any student regNo>","password":"magic"} → returns a valid signed JWT for that student.

Fix

Delete the if ("magic".equals(...)) branch. Treat magic like any other password. Add tests that assert magic does not authenticate. Audit git history for tokens issued while it existed.

src/main/java/com/pragatix/modules/authentication/service/AuthService.java:178
CriticalC-02Database credentials committed to repository
A05A02Secrets

Vulnerability

application.yml contains live DB username/password (root / stharsan1305) plus useSSL=false&allowPublicKeyRetrieval=true. Anyone with repo access (or who later gains it) can connect directly to the production database.

Fix

  • Move to env vars / Secrets Manager: SPRING_DATASOURCE_PASSWORD, use a least-privilege DB user (not root).
  • Enable useSSL=true (+verify server cert).
  • Rotate the current password and JWT secret immediately — treat as compromised.
  • Add application*.yml to .gitignore; commit only application-example.yml.
  • Add a Gitleaks/secret-scan step to CI (a CI workflow exists in .github/workflows/02-backend-security.yml — ensure it runs on path src/main/resources).
src/main/resources/application.yml:12-16
CriticalC-03JWT signing secret hard-coded → forge tokens for any role (incl. SUPER_ADMIN)
A05A07Token Forgery

Vulnerability

jwt.secret=spdms_super_secret_key_..._algorithm is committed. Since the same key signs HS256 and the token type claim is USER, an attacker with the key can mint a token for e.g. admin with type USER and gain full admin/Super-Admin authorization. The key also bypasses "secrets" scanners because it looks like a phrase.

Fix

  • Load from env/secrets; generate a random 32+ byte key; rotate immediately.
  • Use RSA/EC (asymmetric) keys and an issuer/audience; add jti for revocation.
  • Never permit access_token in the query string; restrict to the Authorization header only.
src/main/resources/application.yml:33
CriticalC-04TeacherAttendanceController — no authorization at all
A01BOLAWrite

Vulnerability

GET /api/teacher/attendance/students and POST /api/teacher/attendance/save have no @PreAuthorize. The global rule only requires any authentication, so a student token can save attendance records for arbitrary students, and read the class list (PII).

Exploit

Login as a student → POST /api/teacher/attendance/save with any year/dept/section and statuses → attendance & streak/XP manipulated.

Fix

Add @PreAuthorize("hasAnyRole('ADMIN','TEACHER','CLASS_COORDINATOR')") at class level; validate the teacher is assigned to the section/department & period; check only today/past dates server-side; add per-period duplicate + faculty-scope checks.

CriticalC-06Badge approval controllers expose admin/CC actions to every user
A01PrivEsc

Vulnerability

/api/cc/badge-requests and /api/admin/badge-requests (GET, PUT approve/reject) carry no @PreAuthorize. A student can approve their own badge, and BadgeRequestService.approveRequest blindly grants the badge. The CC controller even comments that object-level checks are missing.

Fix

  • Class-level role guard: CC = hasAnyRole('ADMIN','CLASS_COORDINATOR'); Admin = hasRole('ADMIN').
  • Object check: only the assigned CC / admin may approve requests for their department+section+year.
  • Normalize the rogue hasAnyRole('ROLE_...') usage (see I-01).

CriticalC-07ADMIN can escalate to SUPER_ADMIN via user create/update
A01Privilege Escalation

Vulnerability

POST /api/v1/admin/users (ADMIN) accepts an arbitrary roles set resolved by name and resolveSubRoles auto-creates any sub-role. An admin can craft the request to assign SUPER_ADMIN, ADMIN, or any role — plus updateUser can re-role and toggle active on any account (including a super-admin).

Fix

  • Only SUPER_ADMIN may assign ADMIN/SUPER_ADMIN roles; ADMIN may only create TEACHER/CC.
  • Restrict allowed role/subRole names to a whitelist; block SUPER_ADMIN in the request DTO.
  • Prevent an admin from editing accounts with a higher role than their own (trust-level comparison).
  • Enforce password policy ≥ 10 chars with complexity (see M-07).
